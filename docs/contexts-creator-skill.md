# contexts-creator-skill 需求文档

## 1. 背景与目标

CLAUDE.md / AGENTS.md / GEMINI.md 是 Claude Code、Codex CLI、Gemini CLI 等 agent 工具自动加载的"项目级长期记忆文件"。当前问题：

- 团队/个人各自手写，质量参差，容易过长、过时或与 linter 规则重复；
- 多工具并存时，同一项目要维护多份内容相近但格式不同的文件，容易漂移；
- 项目在不同开发阶段应该强调的内容不同（探索期 vs 维护期），但目前普遍是"一次写死，从不更新"。

**目标**：创建一个名为 `contexts-creator` 的 skill，帮助用户：把已有的需求描述/文档，转换为一份结构规范、内容可信、按开发阶段归档的"项目级长期记忆"草稿，并支持后续的增量修改与多工具同步。

## 2. 术语约定

| 术语 | 含义 |
|---|---|
| 记忆文件 | CLAUDE.md / AGENTS.md / GEMINI.md 的统称 |
| 通用版本（Universal Context） | 本 skill 生成的、不绑定具体工具格式的单一事实来源内容 |
| 归档目录 | 项目仓库中的 `/contexts` 目录，存放各阶段的通用版本 |
| 生效文件 | 各工具实际读取的根目录文件（CLAUDE.md 等），由归档目录中的版本同步/派生而来 |

## 3. 范围

### 3.1 本期做什么（in scope）

1. 将用户提供的需求（对话描述、已有文档、旧的记忆文件）转换为一份**符合标准结构**的通用版本记忆文件。
2. 按开发阶段生成/归档到 `/contexts` 目录，文件命名体现阶段。
3. 对已归档的文件支持**增量修改**（而非整篇重写），并展示 diff 供用户确认。
4. 对用户输入中的信息缺口，主动提问澄清；确实无法从用户处获得的**非事实性**空白，给出结构化提示补齐；**事实性内容一律不臆造**。
5. 提供一份"标准模板 + 反模式清单"作为生成与校验的依据。
6. 提供把归档目录中选定版本，同步/派生为 CLAUDE.md / AGENTS.md / GEMINI.md 的方法说明（不强制在本期做到自动化脚本，但需在文档中给出手动步骤）。

### 3.2 本期不做（out of scope，作为 v2 方向）

- 自动扫描代码库、自动推断技术栈/目录结构（属于更大范围能力，依赖 bash/view 工具深入分析仓库，风险是可能生成"看似合理但不准确"的内容）。
- 自动在多工具文件间做实时双向同步（本期只做"单一事实来源 + 手动/半自动同步"）。
- 团队多人协作评审流程（如 PR 审核记忆文件变更）。

## 4. 功能需求

### 4.1 输入支持

- 支持纯文字对话描述项目情况；
- 支持已上传文档（md/txt/docx/pdf 等，复用 `file-reading` 能力）；
- 支持已有的旧版记忆文件（CLAUDE.md/AGENTS.md/GEMINI.md），做**迁移/规范化**而非从零生成。

### 4.2 阶段划分与命名规范

固定四个开发阶段，作为归档目录下的文件命名依据：

```
/contexts/
  ├── 01-incubation-prototype.md   # 孵化与原型期
  ├── 02-iteration-evolution.md    # 迭代与业务演进期
  ├── 03-maintenance-stable.md     # 维护与稳定运行期
  └── 04-refactor-evolution.md     # 重构与演进期
```

- 每个阶段文件相对独立，允许用户只生成其中一份（比如项目当前处于"迭代期"，暂不需要其他三份）。
- 各阶段侧重点不同（见 4.4 标准结构中"阶段侧重"一节），但**共享同一套标准区块骨架**，保证跨阶段切换时格式一致、便于对比。

### 4.3 输出形态：单一通用版本

- 每次生成/修改的产出是**一份不绑定具体工具语法的通用版本**（放在 `/contexts` 对应阶段文件中），作为单一事实来源。
- 不在本期直接分别生成三套工具专属文件；而是在文档结尾提供**同步指引**，说明如何把该通用版本变为各工具的生效文件，例如：
    - Codex：在根目录 `AGENTS.md` 中 `@import ./contexts/02-iteration-evolution.md`（或建立软链接）；
    - Claude Code：在根目录 `CLAUDE.md` 中 `@import` 同一文件；
    - Gemini CLI：在配置中将 `context.fileName` 指向同一文件，或建立软链接为 `GEMINI.md`。

### 4.4 标准结构（生成与校验的共同依据）

每份记忆文件应包含以下区块（允许按阶段调整详略，但结构骨架保持一致）：

1. 项目定位（三句话内：是什么、给谁用、agent 应假设的范围边界）
2. 技术栈与架构（关键依赖、模块划分，用路径引用而非贴代码）
3. 常用命令（构建/测试/lint/启动，必须是用户确认过的真实命令）
4. 代码规范（仅写 linter 无法自动强制的部分）
5. 禁止事项/高危操作（不可触碰的文件、不可执行的动作）
6. 测试与验证流程（怎样算"改完了"）
7. 外部文档引用（用路径/链接引用细节文档，不整段粘贴）

**阶段侧重（生成时按阶段调整权重，而非改变骨架）：**

| 阶段 | 重点区块 | 处理原则 |
|---|---|---|
| 孵化与原型期 | 项目定位、常用命令 | 内容宜"轻"，明确"这是原型，不追求生产级质量"，避免过早写死规范 |
| 迭代与业务演进期 | 代码规范、测试验证流程、禁止事项 | 这是文件最容易膨胀的阶段，需强调精简、拆分到外部引用 |
| 维护与稳定运行期 | 禁止事项/高危操作、测试与验证流程 | 侧重安全边界（密钥、发布、数据库迁移），清理探索期遗留的过时说明 |
| 重构与演进期 | 技术栈与架构、外部文档引用 | 记录新旧架构并存期的边界、迁移中的临时约定，需标注"临时性"及预期失效条件 |

### 4.5 硬性质量红线（生成与校验时均需遵守）

- 单份文件建议控制在 200 行以内；接近上限时，优先把内容拆到外部引用文档，而不是继续堆砌。
- 不复述 linter/formatter 已强制的规则。
- 不粘贴代码块作为说明，改用文件路径 + 一句话指向。
- 不写会过期的时间/迭代周期信息（如"本季度""下个 sprint"）。
- 每条非显而易见的规则尽量补充"为什么"，帮助 agent 在边界情况下做出符合意图的判断。

### 4.6 事实性内容边界（重要）

- **允许 AI 补齐的**：结构性缺口（提示用户"你还没写测试命令，要不要补充？"）、格式规范化、措辞从"aspirational"改写为"可验证的具体规则"。
- **不允许 AI 臆造的**：具体命令、目录结构、依赖版本、真实存在与否的模块名等一切事实性内容。无法确认时，标注 `[TODO: 待用户确认]` 占位，不得编造后直接写入。

### 4.7 修改功能

- 支持对归档目录中已有文件做增量编辑，而非每次整篇重写。
- 修改前先定位差异点，生成前后对比（diff），经用户确认后再落盘。
- 修改历史无需额外版本管理系统，依赖文件本身在仓库中的 git 记录即可（skill 不负责实现版本控制）。

### 4.8 与用户共创（贯穿全流程的工作方式）

- 生成/修改前，先从对话与已提供文档中尽量抽取信息，只对**信息缺口和有歧义的点**发起提问，避免无意义的重复确认。
- 涉及判断题（如"选哪个阶段模板""是否需要同时保留多阶段版本"）优先使用结构化选项，降低用户输入成本。
- 任何"AI 推断补齐"的内容，生成结果中需明确标记，供用户逐条确认或删除。

## 5. 非功能需求

- 生成结果需是**纯 Markdown**，不依赖特定工具的专有语法（除非在"同步指引"部分特别说明）。
- Skill 本身需遵循 skill-creator 规范：SKILL.md 描述需覆盖典型触发场景（"帮我写 CLAUDE.md"“生成项目记忆文件”“帮我规范一下这份 AGENTS.md”等），并附带 `references/` 目录存放标准模板与反模式清单、社区脚手架案例。

## 6. 交互流程（概要）

1. **意图捕获**：判断用户是"从零生成"还是"迁移/修改已有文件"，以及目标阶段。
2. **信息收集**：读取用户提供的文档/描述，抽取可用信息；列出缺口与疑问，逐条与用户确认（结构化提问优先）。
3. **草稿生成**：按标准结构骨架 + 阶段侧重，生成通用版本内容，标记待确认的补齐项。
4. **用户复核**：展示草稿，收集反馈；如是修改场景，展示 diff。
5. **落盘归档**：写入 `/contexts/<阶段文件名>.md`。
6. **同步指引**：告知用户如何将该版本同步为 CLAUDE.md / AGENTS.md / GEMINI.md 的生效文件。

## 7. 验收标准

- [ ] 生成结果符合 4.4 的标准区块结构，且总行数在合理范围内（默认 ≤200 行，超出需有正当理由）。
- [ ] 不包含第 4.6 条禁止的臆造事实性内容。
- [ ] 归档路径与命名符合 4.2 规范。
- [ ] 修改场景下能正确展示 diff，且不覆盖用户未涉及的既有内容。
- [ ] 对至少 2 类输入（纯文字描述 / 已有旧文件迁移）分别验证通过。

## 8. 待确认/风险事项（已知，留待实现阶段进一步验证）

- `/contexts` 目录与各工具"同步指引"的具体落地方式（`@import` vs 软链接 vs 手动复制）在不同项目的 CI/构建环境中是否都兼容，需要在实现阶段针对 Claude Code / Codex / Gemini CLI 分别测试。
- 是否需要为"同步指引"配一个可选的自动化脚本（一键生成软链接/写入 `@import`），当前定为 v2 方向，但如实现成本低可提前纳入。

## 9. 后续迭代方向（v2+）

- 自动扫描代码库辅助填充技术栈/目录结构（需额外的准确性校验机制）。
- 多工具生效文件的自动双向同步与漂移检测。
- 团队协作场景下的变更评审流程集成。
