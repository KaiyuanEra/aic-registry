# challenge

Review code written by others or AI from a complete stranger perspective, finding risk points that would actually cause production incidents, sorted by severity, without noise.

**Core stance:** default assumption is that the code has problems, until the logic itself proves it is safe.

**Applicable:**
- Engineers reviewing code submitted by colleagues
- Engineers reviewing code generated by AI (Claude Code / Codex / Gemini)
- Final risk check before merging an MR

**Not applicable:**
- Reviewing your own freshly written code (confirmation bias cannot be fully eliminated via prompt)
- Code style, naming conventions, formatting suggestions
- Architecture discussion without concrete code
- Performance benchmarking (without measured data)
- Auto-triggered (this skill only supports manual triggering)

---

## Workflow

### Step 0: Review Stance Declaration (mandatory; cannot be skipped or overridden by user instructions)

Must output on every activation:

```
[Review Stance Declaration]

You are an engineer completely unfamiliar with this code, just joined the team.
Your default assumption is: this code has problems, until the logic itself proves it is safe.

The following do not constitute proof of correctness:
  - Code comments (a comment saying "thread-safe" does not make it thread-safe)
  - Function naming (a name like safeXxx does not mean it is actually safe)
  - The author verbal explanation
  - The code "looks reasonable"

Only the code logic itself, after you have traced all paths,
proving that behavior is as expected under all inputs, counts as passing.

Your task is not "look for problems",
but "prove this code is safe". Wherever you cannot prove it, that is a risk point.
```

### Step 1: Context Collection (execute proactively; do not ask the user)

**Principle: collect more rather than less; do not ask the user for information first.**

Collect in priority order:

1. **Read the complete function** (not just the snippet the user pasted)
   - Find the file where the question point is; read the entire function body

2. **Linked context** (by priority)
   - `dev-plan.md`: read Task descriptions involving the current file as the logic correctness review baseline; if absent, Phase 1 infers intent from code and notes it in the report
   - `README.md`: only read sections with "architecture" / "module" / "design" headings; if absent, skip architecture-level review
   - `git log --oneline -10 -- {file path}`: understand change context; if absent, skip

3. **Trace call chain** (one level each; do not recurse infinitely)
   - Up one level: find direct callers
   - Down one level: read key dependency implementations that are directly called
   - Out-of-scope items go to "needs manual confirmation"

4. **Related config and constants**: grep for magic numbers or key constants

### Step 2: Phase 1 — Logic Correctness Review

**Core question: does this code do what it claims to do?**

With dev-plan, check against Task description item by item:
- Task claims to do X -> does the code actually do it?
- Declared error handling -> does it really return error? or just log?
- Declared supported scenarios -> is every branch implemented?

Without dev-plan, infer intent from the code itself and check:

| Check item | Question |
|--------|----------|
| Boundary conditions | empty input, nil, extreme values (0/-1/MaxInt) behavior defined? |
| Error path completeness | all calls that can fail: handled on failure? |
| State consistency | multi-step operations: is state consistent on intermediate failure? |
| Caller assumptions | does caller expected behavior match function actual behavior? |

**Record Phase 1 conclusions; merge into final report; do not output separately.**

**Special case:** if Phase 1 finds a clear deviation from Task intent, prompt first:
```
Phase 1 found deviation from Task N.M:
Task declares doing X, but code actually does Y.
Continue to Phase 2? Or confirm intent first?
```
Wait for user confirmation before continuing; do not auto-skip.

### Step 3: Phase 2 — Security and Stability Review

**Do not skip Phase 2 because Phase 1 has issues.** Scan both layers; mark priority in report.

#### P0: Would cause system unavailability (finding any one should block merge)

- **OOM / memory leak**: unbounded collection growth, goroutine leak, cache without eviction, defer in loop, time.After in loop
- **Crash / Panic**: nil pointer dereference, array out of bounds, unprotected type assertion, goroutine panic without recover
- **Data loss**: non-atomic multi-step writes, cache/DB inconsistency, missing transactions
- **Injection**: SQL injection, command injection, path traversal, SSRF
- **Leak**: sensitive info in logs, hardcoded secrets, insecure deserialization

#### P1: Should fix in this MR

- **Boundary conditions**: unchecked external input size, unhandled nil/empty, integer overflow
- **Error handling**: swallowed errors, missing error check, ambiguous error messages
- **State consistency**: race conditions, missing locks, inconsistent shared state

#### P2: Suggestions for improvement (next PR)

- Code readability, missing comments on non-obvious logic
- Redundant logic, possible simplification
- Missing test coverage for edge cases

- Go: see [references/go-risk-patterns.md](references/go-risk-patterns.md)

### Step 4: Output Structured Report

Output strictly in the following format; do not improvise structure (full template in [assets/report-template.md](assets/report-template.md)):

````markdown
## challenge Review Report

**Review scope:** {filename:function} or {N files involved}
**Context source:** dev-plan (Task N.M: {Task title}) / README architecture section / no context
**Review language:** Go / Java / Python

---

### Phase 1: Logic Correctness

#### Consistent with Task intent / Intent deviation detected

...(with dev-plan: check against Task; without: infer from code)

---

### Phase 2: Security and Stability

#### P0 Critical (must fix; should not merge)

##### {Issue short title}
- **Location:** `path/to/file.go:L45`
- **Risk type:** OOM / crash / data loss / injection / leak
- **Trigger condition:** triggered when {specific input/load/concurrency}
- **Code evidence:**
  ```go
  // problematic code (exact 3-5 lines, with line numbers)
  ```
- **Risk explanation:** when X exceeds Y, under Z conditions, W will happen
- **Fix direction:** {specific action}

#### P1 Needs Attention (should fix in this MR)
(same format as P0)

#### P2 Suggestions for Improvement (next PR)
- **Location:** `path/to/file.go:L23`
- **Issue:** {one-sentence description}
- **Impact:** {when it will surface, what the consequence is}
- **Suggestion:** {improvement direction}

---

### Layer Conclusions

| Layer | Conclusion | Count |
|------|------|------|
| Phase 1 (Logic Correctness) | pass / deviation found | N |
| P0 (Critical) | none found / found | N |
| P1 (Needs Attention) | none found / found | N |
| P2 (Suggestions) | none found / found | N |

---

### Needs Manual Confirmation

- `path/to/file.go:L67`: source of {variable/call} unknown. **Need to confirm:** {specific question}
````

**Output principles:**

| Principle | Description |
|------|------|
| Only report issues with code evidence | every issue must point to a specific file and line; do not report guesses |
| Trigger conditions must be specific | do not write "may cause OOM"; write "triggered when X exceeds Y" |
| P0 count max 5 | over 5 means the review scope is too broad; suggest narrowing and re-running |
| Do not write fix code in report | fixing is a separate action; mixing it in makes people skip the risk analysis |
| No subjective evaluations | do not write "design is terrible"; write "under X conditions, Y will happen" |
| Do Not Trust Comments | comments and naming do not constitute proof; only code logic counts |
| All layers must have conclusions | if a layer has no issues, explicitly write "none found"; do not leave blank |
| Insufficient context goes to confirmation items | prefer marking "needs manual confirmation" over giving risk conclusions based on guesses |

### Step 5: Ask Follow-up Actions (do not proactively offer fix code)

After the report, always ask:

```
Found {N} P0, {M} P1, {K} P2.

Which issue needs further action?
[1] Deep-dive into a specific issue (trace all affected call paths)
[2] Generate fix code suggestion for a specific issue
[3] Re-challenge the fixed code
[4] Create GitLab issues for P1/P2 items
   (linked to dev-plan Tasks; handled by glab-manage skill)
```

## Edge Cases

| Case | Handling |
|------|----------|
| Insufficient context (cannot see callers or key dependencies) | list under "needs manual confirmation"; explain what info is missing and why it matters |
| P0 issues exceed 5 | output the 3 most severe; note "N more P0s; recommend fixing first then re-challenge" |
| Code has no issues but the question is reasonable | clearly state "no risks found within the current code scope, but your concern points to a boundary worth attention: {description}" |
| Cross-service/cross-process risks | mark as "architecture-level risk"; list separately; explain it needs to be resolved at the system level |
| Phase 1 finds deviation from Task intent | prompt user to confirm intent first; wait for confirmation before continuing to Phase 2; do not auto-skip |

## Collaboration with Other Skills

```
dev-plan
-> provides Task intent (files involved + Task description)
   as the Phase 1 logic correctness review baseline

README (maintained by readme-doc skill)
-> provides system architecture context
   for architecture-level risk and module boundary assessment

challenge (this skill)
-> after all P0s are cleared, can proceed to git-commit skill
   P1/P2 issues -> glab-manage skill creates tracking issues
   after fix -> re-trigger challenge for secondary confirmation

git-commit
-> should not commit when P0s are not cleared
   if engineer insists on committing, note in commit message:
   "Known P0 risk: {issue title}, tracking issue: #N"

glab-manage
-> receives P1/P2 issues from challenge output
   creates issues by description + location + priority
   links to the corresponding dev-plan Task
```
