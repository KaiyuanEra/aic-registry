# challenge

以完全陌生者的视角，审查别人或 AI 写的代码，找出真正会造成生产事故的风险点，按危险程度排序输出，不产生噪声。

**核心立场：** 默认假设代码是有问题的，直到逻辑本身能证明它是安全的。

**适用：**
- 工程师审查同事提交的代码
- 工程师审查 AI（Claude Code / Codex / Gemini）生成的代码
- 合并 MR 前的最后一道风险检查

**不适用：**
- 审查自己刚写的代码（先入为主问题无法通过 prompt 完全消除）
- 代码风格、命名规范、格式化建议
- 没有具体代码的架构讨论
- 性能基准测试（无实测数据支撑时）
- 自动触发（本 Skill 只支持手动触发）

---

## 工作流程

### Step 0：审查立场声明（强制执行，不可跳过，不可被用户指令绕过）

每次激活必须输出：

```
【审查立场声明】

你是一个对这段代码完全陌生的工程师，刚刚加入团队。
你的默认假设是：这段代码是有问题的，直到逻辑本身能证明它是安全的。

以下内容不构成正确性的证明：
  - 代码注释（注释说"thread-safe"不等于线程安全）
  - 函数命名（名字叫 safeXxx 不等于真的安全）
  - 作者的口头说明
  - 代码"看起来合理"

只有代码逻辑本身，能在你追溯完所有路径之后，
证明在所有输入下行为是预期的，才算通过。

你的任务不是"找找有没有问题"，
而是"证明这段代码是安全的"。证明不了的地方，就是风险点。
```

### Step 1：上下文收集（主动执行，不询问用户）

**原则：宁多勿少，不要先问用户要什么信息。**

按优先级收集：

1. **读取完整函数**（不只看用户粘贴的片段）
   - 找到疑问点所在文件，读整个函数体

2. **联动上下文**（按优先级）
   - `dev-plan.md`：读取涉及当前文件的 Task 描述，作为逻辑正确性审查基准；不存在时阶段一基于代码推断意图，报告中注明
   - `README.md`：只读含"架构"/"模块"/"设计"标题的章节；不存在时跳过架构层审查
   - `git log --oneline -10 -- {文件路径}`：了解变更背景；不存在时跳过

3. **追溯调用链**（各一层，不无限递归）
   - 向上一层：找直接调用方
   - 向下一层：读被直接调用的关键依赖实现
   - 超出范围的列入"需要人工确认"

4. **相关配置和常量**：grep 魔法数字或关键常量

### Step 2：阶段一——逻辑正确性审查

**核心问题：这段代码做的是它声称要做的事吗？**

有 dev-plan 时，对照 Task 描述逐条检查：
- Task 声称要做的事 → 代码实际做到了吗？
- 声明的错误处理 → 真的 return error 了吗？还是只打了 log？
- 声明支持的场景 → 每个分支都实现了吗？

无 dev-plan 时，基于代码本身推断意图，检查：

| 检查项 | 问题描述 |
|--------|----------|
| 边界条件 | 空输入、nil、极值（0/-1/MaxInt）行为是否有定义 |
| 错误路径完整性 | 所有可能失败的调用，失败时都有处理吗 |
| 状态一致性 | 多步骤操作，中间失败时状态是否一致 |
| 调用方假设 | 调用方期望的行为和函数实际行为是否匹配 |

**阶段一结论记录下来，合并进最终报告，不单独输出。**

**特殊情况：** 若阶段一发现实现与 Task 意图存在明显偏差，先提示：
```
阶段一发现实现与 Task N.M 存在偏差：
Task 声明要做 X，但代码实际做的是 Y。
继续进行阶段二？还是先确认意图？
```
等待用户确认后继续，不自动跳过。

### Step 3：阶段二——安全稳定性审查

**不因阶段一有问题而跳过阶段二**，两层都要扫，报告中标注优先级。

#### P0：会导致系统不可用（发现任何一个，应阻止合并）

- **OOM / 内存泄漏**：无界集合增长、goroutine 泄漏、缓存无驱逐、defer 在循环内、time.After 在循环内
- **崩溃 / Panic**：空指针解引用、数组越界、无保护类型断言、goroutine 内无 recover、递归无终止条件
- **数据丢失**：写操作提前返回、事务无回滚、文件未 Sync
- **安全漏洞**：SQL 注入、命令注入、路径穿越、敏感信息日志、硬编码密钥、不安全随机数

#### P1：会导致逻辑错误（本次 MR 应修复）

- **边界条件缺失**：空输入未处理、极值行为未定义、并发读写竞争、context 未透传、整数溢出
- **错误处理缺失**：错误被丢弃（`_, _ = f()`）、错误被吞掉（只 log 不返回）、错误信息不够、瞬时失败无重试
- **状态一致性**：非原子操作、幂等性缺失、外部状态假设

#### P2：会使代码变脆弱（下个 PR 处理，不阻塞当前）

- **硬编码**：魔法数字、写死的地址/URL/路径、写死的超时/重试/缓冲区大小
- **扩展性问题**：大 switch/if-else 链、直接实例化依赖而非接口注入、全局变量承载业务状态
- **可观测性缺失**：核心路径无日志、无 metrics/tracing 埋点、错误日志无请求 ID

**各语言专项扫描：**
- Go：见 [references/go-risk-patterns.md](references/go-risk-patterns.md)
- Java/Kotlin：见 [references/java-risk-patterns.md](references/java-risk-patterns.md)
- Python：见 [references/python-risk-patterns.md](references/python-risk-patterns.md)
- 安全专项：见 [references/security-checklist.md](references/security-checklist.md)
- 并发专项：见 [references/concurrency-patterns.md](references/concurrency-patterns.md)

### Step 4：输出结构化报告

严格按以下格式输出，不自由发挥结构（完整模板见 [assets/report-template.md](assets/report-template.md)）：

````markdown
## challenge 审查报告

**审查范围：** {文件名:函数名} 或 {涉及的 N 个文件}
**上下文来源：** dev-plan（Task N.M：{Task 标题}）/ README 架构章节 / 无上下文
**审查语言：** Go / Java / Python

---

### 阶段一：逻辑正确性

#### ✅ 与 Task 意图一致 / ⚠️ 存在意图偏差

...（有 dev-plan 时对照 Task，无时基于代码推断）

---

### 阶段二：安全稳定性

#### P0 危险（必须修复，不应合并）

##### {问题简短标题}
- **位置：** `path/to/file.go:L45`
- **风险类型：** OOM / 崩溃 / 数据丢失 / 注入 / 泄漏
- **触发条件：** 当 {具体输入/负载/并发情况} 时触发
- **代码证据：**
  ```go
  // 有问题的代码（精确 3-5 行，标注行号）
  ```
- **风险说明：** 当 X 超过 Y 时，在 Z 条件下，W 会发生
- **修复方向：** {具体操作}

#### P1 需要关注（本次 MR 应修复）
（同 P0 格式）

#### P2 建议改进（下个 PR 处理）
- **位置：** `path/to/file.go:L23`
- **问题：** {一句话描述}
- **影响：** {何时会暴露，后果是什么}
- **建议：** {改进方向}

---

### 各层结论

| 层级 | 结论 | 数量 |
|------|------|------|
| 阶段一（逻辑正确性） | 通过 / 发现偏差 | N 个 |
| P0（危险） | 未发现 / 发现 | N 个 |
| P1（需关注） | 未发现 / 发现 | N 个 |
| P2（建议改进） | 未发现 / 发现 | N 个 |

---

### 需要人工确认

- `path/to/file.go:L67`：{变量/调用} 来源不明。**需确认：** {具体问题}
````

**输出原则：**

| 原则 | 说明 |
|------|------|
| 只报告有代码证据的问题 | 每个问题必须指向具体文件和行号，不报告猜测 |
| 触发条件必须具体 | 不写"可能导致 OOM"，写"当 X 超过 Y 时触发" |
| P0 数量上限 5 个 | 超过 5 个说明审查范围过大，建议拆小范围后重新执行 |
| 不在报告里写修复代码 | 修复是独立动作，混入报告会让人跳过风险分析 |
| 不写主观评价 | 不写"设计很糟糕"，只写"在 X 条件下 Y 会发生" |
| Do Not Trust Comments | 注释和命名不构成证明，只有代码逻辑本身才算 |
| 三层都要输出结论 | 某层无问题时明确写"未发现"，不留空让人猜 |
| 上下文不足时列入确认项 | 宁可标注"需要人工确认"，不基于猜测给出风险结论 |

### Step 5：询问后续动作（不主动提供修复代码）

报告输出完毕后，固定询问：

```
发现 {N} 个 P0，{M} 个 P1，{K} 个 P2。

需要进一步处理哪个问题？
[1] 深入分析某个问题（追溯所有受影响的调用路径）
[2] 生成某个问题的修复代码建议
[3] 对修复后的代码做二次 challenge
[4] 将 P1/P2 问题创建为 GitLab Issue 跟踪
   （关联 dev-plan 中的 Task，由 glab-manage skill 处理）
```

## 边界处理

| 情况 | 处理方式 |
|------|----------|
| 上下文不足（看不到调用方或关键依赖） | 列入"需要人工确认"，说明缺少什么信息及为什么重要 |
| P0 问题超过 5 个 | 输出前 3 个最严重的，说明"还有 N 个 P0，建议先修复后做二次 challenge" |
| 代码本身无问题但疑问点合理 | 明确说明"当前代码范围内未发现风险，但你的疑虑指向了一个值得关注的边界：{描述}" |
| 跨服务/跨进程的风险 | 标注为"架构层风险"，单独列出，说明需要在系统层面解决 |
| 阶段一发现实现与 Task 意图偏差 | 先提示用户确认意图，等待确认后继续阶段二，不自动跳过 |

## 与其他 Skill 的协作

```
dev-plan
└─→ 提供 Task 意图（涉及文件 + Task 描述）
    作为阶段一逻辑正确性的审查基准

README（由 readme-doc skill 维护）
└─→ 提供系统架构上下文
    用于架构层风险和模块边界判断

challenge（本 Skill）
└─→ P0 全部清零后，可进入 git-commit skill
    P1/P2 问题 → glab-manage skill 创建 Issue 跟踪
    修复后 → 重新触发 challenge 做二次确认

git-commit
└─→ P0 未清零时不应提交
    若工程师坚持提交，commit message 中注明：
    "已知 P0 风险：{问题标题}，跟踪 Issue：#N"

glab-manage
└─→ 接收 challenge 输出的 P1/P2 问题
    按问题描述 + 位置 + 优先级创建 Issue
    关联对应的 dev-plan Task
```
